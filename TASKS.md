# AgroMarketKZ — Этапы работ и задачи

Разбивка [PRD.md](./PRD.md) на этапы и задачи под стек шаблона **[di-sukharev/vibe](https://github.com/di-sukharev/vibe)**.

**Стек:** монорепо на Bun.
- `backend/` — Hono + Cloudflare Workers + Supabase PostgreSQL/Storage + opaque HttpOnly-сессии + Zod.
- `webapp/` — React + Vite, TanStack Query/Form/Router (CSR за авторизацией) — здесь живёт Telegram Mini App.
- `website/` — Astro (публичные SEO-страницы) — **вне scope** для Mini App, опционально под лендинг.
- `packages/contracts/` — общие Zod-схемы и TypeScript-типы.
- Инфраструктура: Supabase PostgreSQL + Storage (БД и фото, dev и прод), Cloudflare Pages/Workers (прод), Playwright (E2E).

Условные обозначения: `[ ]` — не сделано. В скобках — ссылки на разделы PRD.

> операции. Реестр текущего инженерного долга, его приоритеты и acceptance criteria находится
> только в [tech_debt/README.md](./tech_debt/README.md); не дублировать его задачи здесь.

Продуктовые решения по этапу 4 (обсуждение 2026-07-03):

- Первая заявка доступна незарегистрированному Telegram-пользователю и атомарно создаёт его профиль. Обратная связь и реальные прямые контакты требуют регистрации.
- Антиспам: мягкий лимит частоты заявок/сообщений (порядка 5 за 10 минут на пользователя).
- Сбой Telegram-уведомления не ломает создание заявки; отправка идёт в фоне с одним повтором, а источником правды остаётся админ-панель.
- В заявке сохраняется копия названия карточки (читается даже после удаления карточки); переходы статусов свободные.
- Изображения: загрузка напрямую в Supabase Storage по signed URL от бэкенда; сжатие и конвертация HEIC на клиенте; максимум 10 фото на карточку; при удалении карточки файлы удаляются.
- Категорию с карточками удалить нельзя (сначала освободить).
- Карточку с существующими заявками удалить можно свободно — заявка хранит снапшот названия/цены, `card_id` при удалении обнуляется (миграция `0002_card_delete_keeps_requests.sql`).
- У карточки есть явные состояния `черновик / опубликована / архив`: публична только опубликованная и неархивированная карточка.
- Удалённая карточка тихо исчезает из избранного; добавление/удаление избранного идемпотентно.
- Контакты площадки: незаполненные поля не отдаются в API.

Реализация (2026-07-03): весь бэкенд этапа 4 — контракты `packages/contracts/src/{upload,admin}.ts` +
`settings.ts` (`adminPlatformSettingsSchema`), новые `backend/src/lib/{storage,telegramBot,background,rateLimit}.ts`,
роуты `settings/favorites/requests/feedback` и `routes/admin/{categories,cards,uploads,requests,users,settings}.ts`.
Миграция `0002_card_delete_keeps_requests.sql` применена к dev-базе Supabase и проверена транзакционным
драйраном (удаление карточки с заявкой → `card_id` становится `null`, снапшот сохраняется, откат не оставил тестовых
данных). `bun run typecheck` и `bun test` (backend + contracts) проходят. HTTP-прогон curl-флоу из плана
верификации не выполнен в этой сессии — нет `.env`/`backend/.dev.vars` с реальным `TELEGRAM_BOT_TOKEN`;
сделать перед деплоем (Этап 10) или при следующей сессии с локальным окружением.

Продуктовые решения по этапу 5 (обсуждение 2026-07-03):

- Каждая вкладка — независимый стек: помнит открытый экран, скролл и поиск; повторный тап по уже активной вкладке сбрасывает её в корень.
- Две темы — светлая (база) и собственная фирменная тёмная (не серый дефолт Telegram); переключение автоматическое: в Telegram — по `colorScheme` клиента, в браузере — по `prefers-color-scheme`.
- «Назад»: нативная кнопка Telegram (`BackButton`) в дополнение к своей on-screen кнопке; в браузере — только своя. Включена защита от случайного закрытия (`enableClosingConfirmation`, `disableVerticalSwipes`).
- MainButton Telegram не используется — все действия оформлены собственными кнопками в интерфейсе.
- Нижняя навигация скрывается при открытой экранной клавиатуре.
- Сеть: скелетоны при загрузке, кэш показывается мгновенно с фоновым обновлением (задел под нестабильную связь в поле), человекочитаемая ошибка с кнопкой «Повторить».
- Десктоп/широкий экран: адаптивная сетка карточек и контент, ограниченный по ширине, вместо растянутого на весь экран мобильного макета.

Реализация (2026-07-03): TanStack Router подключён code-based деревом маршрутов (`webapp/src/router.tsx`) —
без плагина/кодогенерации; TanStack Form подключён адаптером `webapp/src/lib/form.tsx` (используется с Этапа 6).
Дизайн-токены (primitive → semantic, светлая/тёмная тема) — `webapp/src/styles/{tokens,base,components}.css`.
Telegram SDK расширен в `webapp/src/lib/telegram.ts` (тема, `BackButton`, цвета шапки/фона, closing confirmation)
и `webapp/src/lib/theme.ts` (автосинхронизация темы). Каркас проверен вживую (Playwright, dev-сервер): порядок вкладок,
память/сброс вкладки, on-screen и (потенциально) нативный BackButton, скелетоны и `ErrorState`+«Повторить» на реальном
сбое сети, светлая/тёмная тема, мобильная и широкая раскладка. Список карточек внутри категории и остальные
пользовательские экраны — Этап 6.

- [x] Избранное: список добавленных карточек, переход в карточку, удаление (раздел 8).

Продуктовые решения по этапу 6 (обсуждение 2026-07-03):

- Поиск работает внутри открытой категории; при пустой или скудной выдаче показываем ссылку «Искать во всей вкладке» (API уже поддерживает оба режима).
- Пустая выдача поиска — это лид: «Ничего не найдено» + кнопка сброса + кнопка «Оставить заявку».
- Поиск живой, с задержкой ~0.5 с после окончания ввода; при слабой связи показываем прошлые результаты с индикатором обновления.
- Для услуг сохранены фильтры цены и географии; для товаров добавлены URL-backed фильтры и сортировка по области, группе, форме собственности, местонахождению, цене и объёму.
- Пустые категории (без карточек) скрываем от пользователей; админ видит все. ⚠ Доработка бэкенда: счётчик карточек в категориях или фильтрация пустых.
- Удалённая админом карточка: из избранного исчезает тихо (каскад в БД); при открытии по кэшу/ссылке — экран «Объявление больше недоступно» + кнопки «В каталог» и «Оставить заявку».
- Галерея карточки: свайп + тап открывает фото на весь экран с увеличением (pinch-zoom).
- Сердечко «В избранное» — и на карточках в списке, и внутри карточки.
- Телефон: принимаем ЛЮБОЙ международный номер, не только казахстанский (отмена решения этапа 3 — не терять клиентов с иностранными симками). ⚠ Доработка: `phone.ts` в contracts + бэкенд (регистрация, профиль, заявки) с строгого KZ на общую E.164-валидацию.
- Правки имени/телефона в разовой заявке зарегистрированного пользователя не меняют профиль; новый пользователь создаёт профиль вместе с первой заявкой.
- Экран успеха заявки: анимация галочки + haptic-вибрация без звука; объявление, телефон и ожидание ответа в рабочее время; кнопка «Продолжить просмотр».
- Повторные заявки на ту же карточку разрешены; от спама защищает общий rate limit.
- Ценовой CTA открывает шторку: заявка — главное действие, телефон / WhatsApp / Telegram — вторичные. До регистрации видны только доступные каналы, после регистрации внешний переход требует второго нажатия.

Реализация (2026-07-04): бэкенд-доработки сначала — `phone.ts` переведён на общую E.164-валидацию
(`normalizePhone`/`phoneSchema`, старые `normalizeKzPhone`/`kzPhoneSchema` удалены, 4 потребителя в
contracts обновлены); `listCategories` считает `cardCount` и скрывает категории без карточек через
`join cards` (публичный ответ — новая `categoryListItemResponse`/`categoryListItemSchema`, admin-эндпоинт
не тронут). Webapp: инфраструктура — `apiDelete`, Telegram-хелперы (haptics, `openExternalLink`,
`openTelegramDeepLink`), `queries.ts` (карточки через `useInfiniteQuery` + `keepPreviousData`, favorites,
settings), `lib/favorites.ts` (optimistic toggle), `lib/format.ts`/`sound.ts`/`useDebouncedValue.ts`/
`formErrors.ts`, `updateProfile` в auth-контексте, зависимость `photoswipe`. Новые экраны — `CatalogTab`,
`CategoryScreen` (обе с живым поиском через `?q=`/`?price=` в URL, синхронизировано с tab-памятью),
`CardScreen` (галерея + PhotoSwipe-lightbox, шторка отклика, заглушка «объявление недоступно»),
`GeneralTab`/`ProfileEditScreen`/`FavoritesScreen`/`FeedbackScreen`. Общие компоненты — `CardTile`,
`FavoriteButton`, `CardsList` (IntersectionObserver + «Показать ещё»), `SearchBar`, `PriceFilter`,
`BottomSheet`, `ContactFields`, `SuccessCheck` (haptic + WebAudio-«дзынь», без аудио-ассета), `RequestSheet`
(3 источника заявки, авто-синхронизация профиля, читаемые 429/409/404), `Gallery`. CSS — секции в
`components.css` на существующих семантических токенах (тёмная тема автоматически). Проверено: `bun test`
(backend 48 тестов + contracts 24, включая новые для `phoneSchema`/`toCategoryListItem`), `typecheck` по
всей монорепе — зелёные; сквозной прогон через реальный dev backend + БД (curl с валидной session cookie
существующего пользователя): категории со счётчиками, список/поиск/фильтр карточек, карточка + 404,
избранное add/list/remove, заявки из всех 3 источников (включая международный номер `+994...`,
нормализованный в E.164), повторная заявка на ту же карточку, rate-limit 429 на 6-й заявке подряд,
обратная связь, обновление профиля — все сценарии отработали корректно, тестовые данные из dev-БД удалены
после проверки. Визуальная проверка в браузере (Playwright/Chrome MCP) не выполнена в этой сессии —

Продуктовые решения по этапу 9 (обсуждение 2026-07-13, обновлено 27.08.2026): тесты используют
прямой `POST /auth/telegram` с офлайн HMAC-подписанным `initData`, получают из ответа session
cookie и добавляют её в Playwright context. Credentials не попадают в `localStorage`; тестовые
администраторы изолированы от production allowlist.

Реализация (2026-07-13): `@playwright/test` установлен в корень монорепо, `e2e/` —
`playwright.config.ts` (два `webServer`: backend на 3000 через `/health`, webapp на 5173;
`workers: 1`, т.к. общая dev-БД не рассчитана на параллельные заявки/rate-limit),
`helpers/telegramAuth.ts` (офлайн HMAC-подпись initData + ретрай на транзиентные 5xx),
`helpers/api.ts` (обёртка для setup/teardown через admin API), `helpers/nav.ts`
(обход известного гочи: Vite dev-прокси форвардит `/admin/*` на backend, поэтому прямой
`page.goto("/admin/...")` в dev возвращает JSON вместо SPA — навигация в админку всегда
через клик по ссылке из «Общее»), `fixtures/auth.fixture.ts` (`userPage`/`adminPage` с готовой
session cookie и предзарегистрированным профилем, `freshUserPage`/ad-hoc свежие telegram id для тестов,
создающих заявки — чтобы не делить общий rate-limit 5/10мин с TEST_USER). 8 спеков, все
сценарии из плана + `access-control.spec.ts` (403 от admin API + отсутствие ссылки
«Управление» для обычного пользователя). Добавлены точечные `data-testid` на интерактивные
элементы вебапа (их не было вообще) — регистрация, каталог/карточка, заявки/избранное,
админ-экраны. `bun run test:e2e` — 12/12 зелёных, `bun run typecheck` — зелёный.
Известное ограничение: общий dev-Supabase не подходит для параллельных CI-прогонов
(нужна отдельная БД/ветка на прогон) — see e2e/playwright.config.ts.

Текущая конфигурация supersedes это ограничение: `e2e/playwright.config.ts` не наследует
корневой `.env`, требует отдельные `E2E_*` DB/Storage/Telegram значения, запускает
серверы с явным окружением и проверяет, что тестовые ресурсы не совпадают с production.
Для удалённых E2E-БД/Supabase корневой `.env` с production baseline обязателен; полностью
локальная конфигурация может работать без него.
Каждый прогон получает уникальный префикс и отдельные synthetic Telegram ids, удаляет только свои
карточки, категории, заявки, feedback, Storage и тестовые профили; старые leftovers
удаляются вручную после проверки отсутствия активных прогонов.
