# Аудит безопасности AgroMarketKZ

**Дата:** 2026-07-08
**Скоуп:** backend (Hono/Bun/Cloudflare Workers), webapp (React/Vite), контракты (Zod), схема БД (Postgres/Supabase), Storage, CI.
**Контекст:** релиз в прод через 4 дня, активная аудитория ~24 000 пользователей.
**Метод:** ручной чтение-аудит всех исходников + проверка живого проекта Supabase (security-advisors, состояние RLS, конфиг Storage).

---

## Итоговая оценка

**Общий вердикт: продукт можно выпускать после устранения блокеров ниже. Критических (8–10) уязвимостей не найдено.**

Кодовая база в хорошем состоянии по безопасности:
- SQL-инъекций нет — все запросы параметризованы через tagged-templates `postgres.js`.
- Проверки подписи Telegram (initData, Login Widget, requestContact, webhook-secret) реализованы корректно, со сравнением за постоянное время.
- Авторизация админа — по неизменяемому `telegram_id`, живой проверкой на каждый запрос.
- XSS-векторов в приложении нет: React экранирует вывод, `dangerouslySetInnerHTML` не используется, уведомления в Telegram HTML-экранируются.
- RLS включён на всех таблицах (deny-all для anon), бэкенд ходит под ролью `postgres` в обход RLS — прямой доступ к PII через Supabase REST API закрыт.

Найденные проблемы — это **hardening и устойчивость под нагрузку**, а не пробитие периметра. Шкала оценки: **10 = критично, 1 = косметика.**

## Детальный разбор и план доработок

### M1 — Долгоживущий JWT в localStorage без возможности отзыва · оценка 6

**Где:** `backend/src/lib/jwt.ts` (TTL 30 дней), `webapp/src/lib/token.ts` (localStorage).

**Суть.** Токен живёт 30 дней, хранится в `localStorage`, у бэкенда нет ни denylist, ни `jti`, ни версии сессии. Отозвать один скомпрометированный токен нельзя — только ротация `JWT_SECRET`, которая разлогинит всех 24k. При утечке токена (чужое устройство, вредонос, будущий XSS) атакующий получает до 30 дней доступа к аккаунту.

**Почему не выше.** Прямого канала утечки сейчас нет (XSS не найден), привилегии обычного пользователя невелики (свои заявки/избранное, PII только собственная). Админ-права в токене не зашиты — проверяются вживую по allowlist, так что украденный токен рядового юзера не даёт админку.

**План (под мою ответственность):**
1. **Сейчас (обязательный минимум):** добавить в claims `ver: number` (версия сессии) и `iat`. В `users` — колонку `token_version int not null default 0`. `verifyToken` сверяет `payload.ver` с текущим `token_version` пользователя. Это даёт кнопку «разлогинить пользователя» (инкремент версии) без ротации общего секрета. Проверку делать в `requireAuth` тем же запросом, что и `requireRegistered` (объединить в один SELECT, чтобы не добавлять раунд-трип — см. также M5).
2. **Сейчас:** сократить TTL до 7–14 дней; в Mini App повторный тихий вход по `initData` бесшовный, так что пользователь не заметит.
3. **После релиза:** рассмотреть refresh-токен + короткий access-токен. Не блокер.
4. Хранение в `localStorage` для Telegram Mini App приемлемо; переезд на httpOnly-cookie в Mini App-контексте нетривиален (кросс-домен, отсутствие cookie в WebView) — оставляем, но закрываем M4 (CSP) как компенсирующий контроль.

### M2 — Нет rate-limiting / анти-DoS на публичных и auth-эндпоинтах · оценка 6 · БЛОКЕР

**Где:** `backend/src/routes/settings.ts` (публичный, без авторизации), `backend/src/routes/auth.ts` (`/auth/telegram`, `/auth/widget`), `app.ts` (нет глобального лимитера).

**Суть.** Единственный анти-абуз — мягкий лимит 5/10 мин на заявки и обратную связь, считающийся COUNT-запросом в БД (`rateLimit.ts`). На всё остальное лимитов нет:
- `GET /settings` — без авторизации, бьёт в БД на каждый вызов. Идеальная цель для флуда: дёшево слать, дорого обслуживать (чтение строки БД × RPS).
- `POST /auth/telegram` и `/auth/widget` — на каждый запрос считают HMAC-SHA256 (CPU), до проверки подписи в БД не ходят (это плюс), но CPU-флуд возможен.
- При 24k аудитории даже органический пик логинов (рассылка → все разом открыли Mini App) даёт всплеск на auth + `/profile` + `/catalog`.

**План (под мою ответственность):**
1. **Обязательно до релиза:** включить rate-limiting на уровне Cloudflare (WAF Rate Limiting Rules) для `/*` — например 60–120 req/min на IP, и отдельное жёсткое правило на `/auth/*` (10–20/min на IP) и `/settings` (30/min на IP). Это фронт-барьер, не трогающий код.
2. **Обязательно:** кешировать `GET /settings` — данные меняются раз в месяц. Отдавать `Cache-Control: public, max-age=300` и полагаться на кеш Cloudflare (либо KV-кеш), чтобы флуд не доходил до БД.
3. **Желательно:** глобальный middleware-лимитер в Hono по IP (заголовок `CF-Connecting-IP`) на изменяющие эндпоинты, с хранением счётчиков в Cloudflare KV/Durable Object (in-memory на Workers не переживёт изоляты). Если не успеваем — п.1 закрывает риск на релиз.
4. Ретёрнить `Retry-After` на 429.

### M3 — Нет лимита размера тела запроса · оценка 5 · БЛОКЕР

**Где:** все роуты через `await c.req.json()`; Zod-валидация (`MAX_IMAGES=10`, `DESCRIPTION_MAX=3000` и т.д.) применяется **после** полного парсинга тела в память.

**Суть.** Любой авторизованный пользователь (из 24k) может отправить многомегабайтный JSON (например, гигантский массив объектов до срабатывания `.max(10)`). Тело целиком читается и парсится в память Worker/Bun до того, как Zod его отклонит. Умноженное на конкуренцию — давление на память и CPU (парсинг).

**План (под мою ответственность):**
1. **Обязательно до релиза:** глобальный middleware, отклоняющий запросы с `Content-Length` больше порога (например 256 КБ для JSON-роутов; загрузка картинок идёт напрямую в Storage по signed URL, минуя бэкенд, так что бэкенду большой лимит не нужен). Вернуть 413.
2. На Cloudflare добавить WAF-правило на размер тела как второй рубеж.
3. Проверять `Content-Length` до `c.req.json()`; для chunked без длины — ограничивать чтение.

### M4 — Нет security-заголовков / CSP на webapp · оценка 5

**Где:** webapp хостится на Cloudflare Pages; заголовки безопасности не заданы (`_headers` отсутствует). API-ответы тоже без заголовков.

**Суть.** Нет `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`/`frame-ancestors`. XSS в приложении не найден, но CSP — это defense-in-depth: при появлении XSS (свой код, зависимость, компрометация Telegram widget-скрипта, который в браузерном логине грузится с `telegram.org`) она ограничивает эксфильтрацию JWT из localStorage. Особенно важно в связке с M1.

**План (под мою ответственность):**
1. Добавить `webapp/public/_headers` (Cloudflare Pages) с:
   - `Content-Security-Policy` — `default-src 'self'`; `connect-src` — API-домен + `https://*.supabase.co` (картинки/аплоад); `script-src 'self' https://telegram.org` (виджет); `img-src 'self' https://*.supabase.co data:`; `frame-ancestors https://web.telegram.org https://*.telegram.org` (Mini App работает в iframe Telegram Web) — проверить, что не ломает встраивание.
   - `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (отключить лишнее).
2. Прогнать в Telegram Web + мобильном клиенте, скорректировать `frame-ancestors`/`connect-src` под реальные домены.
3. `frame-ancestors` критично не перекрыть, иначе Mini App перестанет открываться в вебе. Тестировать до раскатки на всех.

### M5 — Риск исчерпания пула соединений к БД под нагрузкой 24k · оценка 5 · БЛОКЕР (доступность)

**Где:** `backend/src/db.ts` — `postgres(env.DATABASE_URL, { prepare: false })` без явного `max`; каждый роут открывает соединения; часть роутов делает 2–4 последовательных запроса (`requireRegistered` + основной, `getCardById` — 3 запроса).

**Суть.** Это про доступность (тоже часть безопасности для лончта). На Cloudflare Workers каждый изолят держит свой пул; при 24k и множестве изолятов число TCP-соединений к Supabase-пулеру может упереться в лимиты плана. `requireRegistered` добавляет отдельный SELECT к каждому защищённому запросу — лишний раунд-трип и соединение.

**План (под мою ответственность):**
1. **Обязательно до релиза:** явно задать `max` в `postgres()` (небольшой, 3–5 на изолят) и `idle_timeout`/`connect_timeout`. Убедиться, что `DATABASE_URL` указывает на **transaction pooler** Supabase (порт 6543) — по `.env.example` так и есть.
2. Проверить лимиты соединений тарифа Supabase против ожидаемой конкуренции; при необходимости включить/поднять пулер.
3. Объединить `requireAuth` + `requireRegistered` (+ проверку `token_version` из M1) в один SELECT в middleware, чтобы убрать лишний запрос на каждый защищённый вызов.
4. Нагрузочный тест (k6/artillery) на сценарий «пик логинов + листинг каталога» до раскатки на всю аудиторию.

### L1 — Публичный бакет `card-images` разрешает листинг всех файлов · оценка 4

**Где:** `database/supabase/storage.sql` — политика `card-images public read` (`for select using bucket_id=...`). Supabase-advisor подтверждает: `public_bucket_allows_listing`.

**Суть.** Для публичного бакета доступ по прямому URL объекта работает **без** этой SELECT-политики. Наличие широкой SELECT-политики дополнительно разрешает **листинг** всего бакета — любой может перечислить все загруженные файлы (`cards/<uuid>.<ext>`), включая orphaned-загрузки (L9) и любое случайно загруженное изображение. Сами фото товаров публичны, так что утечка невелика, но перечисление лишнего — нежелательно.

**План:** удалить/сузить SELECT-политику на `storage.objects` для `card-images` (оставить только публичный object-access, без листинга). Проверить, что фото в каталоге по-прежнему открываются по публичному URL. [remediation](https://supabase.com/docs/guides/database/database-linter?lint=0025_public_bucket_allows_listing)

### L2 — Прод-CORS `WEBAPP_ORIGIN` = localhost-плейсхолдер · оценка 3 · БЛОКЕР (функциональный)

**Где:** `backend/wrangler.toml` `[vars] WEBAPP_ORIGIN = "http://localhost:5173"`; `app.ts` фолбэк `?? "http://localhost:5173"`.

**Суть.** Не уязвимость (авторизация на Bearer-токенах, cookie не используются — CORS тут не рубеж безопасности), но при деплое без переопределения `WEBAPP_ORIGIN` браузерный (не-Telegram) вход сломается: браузер заблокирует запросы с реального origin. Есть и обратный риск — соблазн поставить слишком широкий origin.

**План:** перед деплоем задать `WEBAPP_ORIGIN` на реальный домен webapp (Cloudflare Pages URL). Не использовать `*`. Добавить в чек-лист релиза проверку всех прод-`[vars]`/secrets (там же плейсхолдеры `SUPABASE_URL`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_MINIAPP_SHORTNAME`).

### L3 — Signed upload не ограничивает MIME/размер на сервере · оценка 3

**Где:** `backend/src/lib/storage.ts` `createSignedUploadUrl` — signed URL не фиксирует content-type/размер; Storage-лимит файла 50 МБ (проверено в конфиге).

**Суть.** Эндпоинт админ-only (`requireAdmin`), поэтому риск ограничен доверенным кругом. Но signed URL позволяет залить произвольный тип/до 50 МБ; клиентская валидация MIME обходится.

**План:** при выпуске signed URL передавать ожидаемый `content-type` и разумный `max size` (Supabase поддерживает ограничения на signed upload); либо снизить `fileSizeLimit` бакета до, например, 8 МБ. Приоритет низкий (админ-only).

### L4 — Слабый rate limit заявок/фидбэка, нет глобального · оценка 3

**Где:** `backend/src/lib/rateLimit.ts` + `repos/*` COUNT-запросы.

**Суть.** Лимит 5/10 мин только per-user и только на заявки/фидбэк; каждый вызов — COUNT в БД (доп. нагрузка, см. M5). Против распределённого абуза (много аккаунтов) не защищает. Закрывается глобальным лимитером из M2.

**План:** после M2 — оставить как есть или перенести счётчик в KV. Не блокер.

### L5 — `search_path` mutable у функции `set_updated_at` · оценка 2

**Где:** `database/migrations/0001_initial_schema.sql`, функция-триггер. Advisor: `function_search_path_mutable` (WARN).

**Суть.** Функция без фиксированного `search_path` — теоретический вектор при эскалации через подмену объектов в `search_path`. Функция простая (`new.updated_at = now()`), риск минимальный.

**План:** пересоздать с `set search_path = ''` (или `pg_catalog`) в определении. [remediation](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable)

### L6 — Zod `issues` в теле ошибок 400 · оценка 2

**Где:** `backend/src/app.ts` `onError` → `{ error, issues: err.issues }`.

**Суть.** Ответ раскрывает имена полей/структуру схемы. Не критично (схема и так выводима из контрактов), но лишняя информация наружу.

**План:** в проде отдавать компактное сообщение без полного `issues` (или маппить в короткий список «поле → сообщение»). Низкий приоритет.

### L7 — `verifyToken` не валидирует форму payload · оценка 2

**Где:** `backend/src/lib/jwt.ts` — `verify(...) as unknown as TokenClaims`, затем `String(sub)`/`Number(tgId)`.

**Суть.** Подпись проверяется (`HS256` задан явно — алгоритм-конфьюжн с `alg=none` исключён), но структура claims не валидируется в рантайме. При валидной подписи содержимое доверенное, так что риск теоретический.

**План:** прогнать payload через маленькую Zod-схему (`sub: uuid`, `tgId: number`, `exp: number`) и отклонять невалидное. Заодно закрывает будущие ошибки. Совместить с изменениями M1.

### L8 — Внешние ссылки из настроек площадки без валидации схемы · оценка 2

**Где:** `webapp/src/lib/format.ts` `telegramLink` (пропускает `https?://…` как есть), `CardScreen`/`FeedbackScreen` — `tel:`/`mailto:`/`openExternalLink`.

**Суть.** Значения задаёт админ (доверенный, малый круг). `contactPhone`/`whatsappPhone` нормализованы в E.164, `email` валиден. `telegramContact` — свободная строка до 100 симв., пропускается в ссылку. Компрометация/ошибка админа могла бы подставить нежелательный URL.

**План:** в `telegramLink` разрешать только `https://t.me/…` и голые handle; для `openExternalLink` — whitelist схем (`https`, `tel`, `mailto`, `https://wa.me`). Низкий приоритет.

### L9 — Orphaned-загрузки в Storage накапливаются · оценка 2

**Где:** `backend/src/routes/admin/uploads.ts` — принятый MVP-долг (комментарий в коде).

**Суть.** Не security, а мусор в Storage: signed URL выдан, но карточка не создана → файл висит. Усугубляется L1 (листингом их видно).

**План:** периодическая уборка объектов `cards/*`, не привязанных к `card_images` (cron/Edge Function), старше N дней. После релиза.

## Что сделано правильно (сохранить при доработках)

- **Параметризованный SQL везде** — включая динамические `sql(columns, ...keys)` и `tx(rows, ...)`; `escapeLike` для `ILIKE`. Инъекций нет.
- **Проверка Telegram-подписей** — initData (HMAC c `WebAppData`), Login Widget (`SHA256(bot_token)`), requestContact, webhook-secret — по спецификации, со сравнением за постоянное время и проверкой свежести `auth_date`.
- **Верификация владельца контакта** — `contact.userId === telegramId` перед сохранением `verified_phone`.
- **Админка** — allowlist по неизменяемому `telegram_id`, живая проверка (снятие прав действует мгновенно), username игнорируются.
- **RLS включён на всех таблицах** без политик = deny-all для anon/authenticated ролей PostgREST; бэкенд под ролью `postgres` в обход RLS. Прямой доступ к PII через Supabase REST закрыт.
- **Валидация UUID** параметров пути (`z.uuid().safeParse`) до запросов в БД.
- **Секреты** — в `.gitignore`, на проде через `wrangler secret put` (не в `[vars]`); в коде не захардкожены.
- **Фоновые задачи** — через `executionCtx.waitUntil` с `.catch`, без необработанных reject.
- **Экранирование** — React по умолчанию; Telegram-уведомления через `escapeHtml`; `dangerouslySetInnerHTML`/`eval` отсутствуют; `window.open` c `noopener,noreferrer`.
- **Единый источник лимитов** (`contracts/constants.ts`) для фронта и бэка — валидация не расходится.

## Приоритетный план на 4 дня

**День 1 — блокеры доступности/DoS (M2, M3, M5)**
- Cloudflare WAF: rate-limit на `/*`, `/auth/*`, `/settings`; правило на размер тела.
- Middleware лимита `Content-Length` (413).
- `postgres()` — явные `max`/`idle_timeout`; подтвердить transaction pooler; объединить auth+registered в один SELECT.
- Кеш `GET /settings` (`Cache-Control` + Cloudflare).

**День 2 — auth-hardening (M1, L7)**
- `token_version` в `users` + claim `ver`; проверка в middleware; кнопка «разлогинить».
- TTL JWT → 7–14 дней. Zod-валидация payload.

**День 3 — периметр и конфиг (M4, L1, L2, L5)**
- `_headers` с CSP/остальными заголовками; прогнать в Telegram Web и мобильном.
- Сузить SELECT-политику бакета (убрать листинг).
- Задать прод-`WEBAPP_ORIGIN` и проверить все прод-vars/secrets по чек-листу.
- Зафиксировать `search_path` функции.

**День 4 — нагрузочный тест, регресс, мелочи (M5, L3, L6, L8)**
- Нагрузочный тест «пик логинов + каталог»; проверить соединения к БД под нагрузкой.
- Ограничение MIME/размера на signed upload (или снизить лимит бакета).
- Компактные ошибки без `issues` в проде; whitelist схем ссылок.
- Финальный прогон `get_advisors` (security) — убедиться, что WARN-и закрыты.

**После релиза (не блокеры):** refresh-токены, KV-лимитер, уборка orphaned-загрузок, перенос rate-count из БД.
