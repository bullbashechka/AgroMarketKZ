## Детали и план доработок

### 1. Тестовый admin id `900000002` в `ADMIN_ALLOWLIST` — 9/10

**Где:** `.env:ADMIN_ALLOWLIST=1295392762,900000002`, `.env.e2e.example:E2E_TEST_ADMIN_TG_ID=900000002`,
`backend/src/lib/admin.ts`, `DEPLOYMENT.md` («секреты заданы через `wrangler secret put`»).

**Суть.** E2E-тесты подписывают `initData` офлайн настоящим `TELEGRAM_BOT_TOKEN`
(`e2e/helpers/telegramAuth.ts`) и требуют, чтобы `E2E_TEST_ADMIN_TG_ID` присутствовал
в `ADMIN_ALLOWLIST`. Значение `900000002` лежит внутри **реально выданного** диапазона
Telegram id (аккаунты примерно 2019–2020 гг.), то есть с высокой вероятностью принадлежит
живому постороннему человеку. Если этот id попал в прод-секрет (а он с большой вероятностью
скопирован из `.env`), владелец аккаунта получает полный админ-доступ простым открытием
Mini App: `GET /admin/users` отдаёт имена и телефоны всех 24k пользователей, `GET /admin/requests`
— все заявки с контактами, `PATCH /admin/settings` позволяет увести `adminChatId` на свой чат,
`DELETE /admin/cards/:id` — удалить каталог.

Проверка `isAdmin` живая, статус не зашит в токен — это правильно и означает, что фикс
вступает в силу немедленно после смены секрета.

**План.**
1. Немедленно переустановить прод-секрет только реальными id:
   `echo -n "1295392762" | wrangler secret put ADMIN_ALLOWLIST`.
2. Разнести E2E и прод: тестовый id держать только в `.env.e2e`, а `ADMIN_ALLOWLIST`
   для E2E задавать через отдельный dev-Worker / локальный `.dev.vars`.
3. Добавить в `parseAllowlist` отбраковку id вне разумного диапазона реальных аккаунтов
   и `console.warn` при пустом списке — чтобы «пустой allowlist» был виден в логах, а не тих.
4. Пройтись по `GET /admin/users` и `GET /admin/requests` в логах Cloudflare за период
   с момента деплоя — убедиться, что обращений с чужого id не было.

### 2. `AUTH_RATE_LIMITER` 10 запросов/мин по IP — 9/10

**Где:** `backend/wrangler.toml` (`AUTH_RATE_LIMITER`, limit 10 / period 60),
`backend/src/middleware/rateLimit.ts:enforceAuthRateLimit` (ключ — `CF-Connecting-IP`).

**Проверено на проде:** 11 запросов к `/auth/telegram` прошли, 12-й вернул `429`. Лимитер живой.

**Суть.** `/auth/telegram` вызывается при каждом холодном старте Mini App без токена
(`webapp/src/lib/auth.tsx:bootstrapProfile`) и повторно на каждом `401`. Мобильные операторы
Казахстана работают через CGNAT — тысячи абонентов за одним публичным IP. На запуске с рассылкой
по 24k пользователей десять входов в минуту с одного IP выбираются мгновенно, и легитимные
пользователи получают «Слишком много запросов» на самом первом экране. Это наиболее вероятный
сценарий провала запуска — причём он не выглядит как инцидент в метриках бэкенда.

Дополнительно: ключ по `CF-Connecting-IP` с фолбэком `"unknown"` складывает все запросы
без заголовка в одно ведро.

**План.**
1. Поднять лимит до значения, осмысленного для CGNAT: `limit = 600, period = 60`
   (десять входов в секунду с одного egress IP — всё ещё защита от брутфорса,
   но не помеха реальному трафику).
2. Ключевать не только по IP: для `/auth/telegram` использовать составной ключ
   `IP + telegram_id из initData` — тогда один пользователь ограничен жёстко,
   а соседи по NAT друг другу не мешают. Извлекать id до валидации подписи можно
   без риска: он используется только как ключ лимитера.
3. Убрать бесконечный цикл повторного входа: в `bootstrapProfile` на `429`
   показывать экран «Попробуйте через минуту» с `Retry-After`, а не повторять запрос.
4. Реальную защиту от брутфорса перенести на Cloudflare WAF Rate Limiting
   (там доступны ASN, JA3, managed challenge) — это профильный инструмент.

### 3. RLS включён вручную в проде и не зафиксирован в миграциях — 8/10

**Где:** `database/migrations/*.sql` — ни одного `enable row level security`.

**Проверено на проде:**

| Таблица | RLS | Политик | Грантов у `anon`/`authenticated` |
|---|---|---|---|
| users, requests, feedback_messages, cards, card_images, card_specs, categories, favorites, platform_settings | `true` | 0 | 14 |

Supabase Security Advisor подтверждает: `rls_enabled_no_policy` (INFO) по всем девяти таблицам.

**Суть.** Текущий прод **безопасен**: RLS включён, политик нет — значит `anon`/`authenticated`
не получают ни одной строки, а backend ходит под `service_role`, который RLS обходит.

Проблема в том, что это состояние существует только в живой БД и нигде не описано кодом.
Любое пересоздание окружения — staging, восстановление из дампа, миграция на новый проект,
`db reset` — поднимет схему **без RLS**. При этом `anon` и `authenticated` сохраняют полные
гранты на все таблицы (14 привилегий), то есть RLS — единственный барьер, защиты в глубину нет.
Цена ошибки: полный дамп `users` (имена + телефоны 24k человек) и `requests` по публичному
anon-ключу.

**План.**
1. Добавить `database/migrations/0009_enable_rls.sql`: `alter table … enable row level security`
   для всех девяти таблиц (идемпотентно — на текущем проде no-op).
2. В той же миграции — защита в глубину:
   `revoke all on all tables in schema public from anon, authenticated;`
   и `alter default privileges in schema public revoke all on tables from anon, authenticated;`
   Backend работает через `service_role` и прямое подключение, эти гранты ему не нужны.
3. Добавить в чек-лист «Проверки перед деплоем» (`DEPLOYMENT.md`) прогон
   `get_advisors(type=security)` и требование нулевых ERROR/WARN.

### 4. БД недоразмерена под 24k + один SELECT авторизации на каждый запрос — 8/10

**Где:** `backend/src/middleware/auth.ts:26` (`findAuthUser` на каждом запросе),
`backend/src/db.ts:POSTGRES_POOL_OPTIONS` (`max: 3` на изолят), `backend/wrangler.toml`.

**Проверено на проде:** PostgreSQL 17.6, `shared_buffers = 28672` блоков ≈ **224 МБ**
(инстанс уровня Micro, ~1 ГБ RAM), `max_connections = 60`, размер БД 11 МБ,
данных пока почти нет (3 пользователя, 1 карточка, 1 заявка).

**Суть.** Три множителя нагрузки складываются:
- `requireAuth` делает `SELECT token_version, registered_at FROM users` **на каждый**
  аутентифицированный вызов API, до любого кеша. Это пол приложения по числу запросов.
- Cloudflare Workers без Hyperdrive: каждый холодный изолят открывает новый TCP+TLS
  до Supavisor. Изолятов много (по колокациям), `max: 3` — на каждый.
- `max_connections = 60` на инстансе; Supavisor мультиплексирует, но его собственный
  pool_size на Micro невелик.

Нагрузочный тест в репозитории есть (`e2e/scripts/loadTest.ts`), но ограничен сверху
2000 пользователями и, судя по документации, на прод-профиле не гонялся.

**План.**
1. Поднять инстанс Supabase минимум до Small/Medium **до** запуска — это единственное
   изменение, которое нельзя сделать быстро после инцидента.
2. Подключить **Cloudflare Hyperdrive** как прослойку к Supavisor: это снимает
   TCP+TLS-хендшейк с холодных стартов и даёт пуллинг на стороне Cloudflare.
   Замена сводится к смене `DATABASE_URL` на биндинг Hyperdrive.
3. Убрать SELECT из горячего пути: кешировать `{tokenVersion, isRegistered}` по `userId`
   в Workers KV с TTL 60 с. Отзыв сессии тогда вступает в силу с задержкой до минуты —
   для `revoke-sessions` это приемлемо; при желании инвалидировать ключ явно в
   `revokeUserSessions`.
4. Прогнать `bun run load:test` на максимуме (2000 пользователей, concurrency 200)
   против прод-конфигурации и зафиксировать p95/p99 и `poolSignals`.
5. Настроить алерты: ошибки подключения к БД, доля 5xx, `wrangler tail` в Logpush.

### 5. Верификация телефона недостижима после регистрации — 6/10

**Где:** `backend/src/routes/profile.ts:55-61` (`PUT /`), `backend/src/repos/users.ts:updateContacts`,
`webapp/src/components/ContactFields.tsx:18-21`.

**Суть.** Два разрыва в одной цепочке:
- Контракт `updateProfileInput = registerInput` **принимает** `contactResponse`, но обработчик
  `PUT /profile` его игнорирует: `updateContacts` пишет только `contact_name` и `contact_phone`.
- На клиенте `ContactFields.handleShareContact` берёт из `sharePhoneFromTelegram()` только
  `.phone` и **выбрасывает** `.contactResponse`. `ContactFields` используется в `ProfileEditScreen`
  и `FeedbackScreen` — там подписанный proof теряется ещё до отправки.

Итог: подтвердить телефон можно только в момент первой регистрации или первой заявки.
Пользователь, сменивший номер, навсегда теряет ✓, а админ в уведомлении видит
неподтверждённый контакт. Это подрывает саму ценность фичи верификации.

**План.**
1. `ContactFields`: добавить необязательный проп `onContactResponseChange` и пробрасывать
   `shared.contactResponse` наверх; сбрасывать его при ручном редактировании поля
   (как уже сделано в `RequestSheet:153`).
2. `PUT /profile`: вызвать `tryValidateContactPhoneForUser(data.contactResponse, telegramId, env)`
   и передать результат в `updateContacts`, повторив логику `case when … then … else verified_phone end`
   из `register()`.
3. `ProfileEditScreen` и `FeedbackScreen`: хранить `contactResponse` в состоянии и слать его.
4. Тест: смена номера с новым proof → `phoneVerified: true`; смена без proof → `false`.

### 6. Бот отвечает приветствием на любое личное сообщение — 6/10

**Где:** `backend/src/lib/telegramWebhook.ts:78-80`.

**Суть.** Комментарий обещает «`/start` greeting», но код возвращает `greet` на **любое**
сообщение в приватном чате. При 24k пользователей это значит: каждое сообщение боту —
исходящий `sendMessage`. Bot API ограничивает бота примерно 30 сообщениями в секунду
глобально; исчерпав лимит на приветствиях, бот перестанет доставлять уведомления
о заявках в админ-чат. Плюс тривиальный abuse: один человек в цикле пишет боту и выжигает квоту.

**План.**
1. Отвечать только на `message.text === "/start"` (и, при желании, `/help`).
2. Добавить дедупликацию: не приветствовать один и тот же `chat_id` чаще раза в час
   (Workers KV с TTL).
3. Развести приоритеты: уведомления о заявках отправлять с ретраем, приветствия — без.

### 7. Данные Login Widget валидны 24 часа и проходят через query string — 6/10

**Где:** `backend/src/lib/telegram.ts:6` (`MAX_AUTH_AGE_SEC = 24h`, общий для обоих путей),
`webapp/src/screens/LoginScreen.tsx:63` (`data-auth-url`).

**Суть.** Выбор `data-auth-url` вместо `data-onauth` правильный — он избавил от `unsafe-eval`
в CSP. Но подписанные данные (включая `hash`) прилетают в query string и остаются валидными
сутки. Кто угодно, получивший этот URL — из истории браузера, синхронизации профиля,
корпоративного прокси, скриншота, — может воспроизвести его на `/auth/widget` и получить
JWT на 14 дней. `window.history.replaceState` чистит адресную строку, но не источники выше.

Для `initData` окно в 24 часа оправдано (строка живёт всю сессию Mini App), для
widget-редиректа — нет: редирект происходит мгновенно.

**План.**
1. Развести окна свежести: оставить 24 ч для `validateInitData`, ввести
   `WIDGET_MAX_AUTH_AGE_SEC = 300` для `validateWidgetLogin`.
2. Сделать widget-логин одноразовым: хранить `hash` в Workers KV с TTL 300 с
   и отклонять повтор.
3. Проверить, что на `/auth/widget` действует `Referrer-Policy: no-referrer` (уже стоит
   глобально в `app.ts` — подтвердить, что заголовок доходит до редиректной страницы Pages,
   где сейчас `strict-origin-when-cross-origin`).

### 9. `storagePath` не валидируется по шаблону — 5/10

**Где:** `packages/contracts/src/card.ts:37` (`requiredText(STORAGE_PATH_MAX)`),
`backend/src/lib/storage.ts:9` (`publicImageUrl` не кодирует path),
`backend/src/lib/storage.ts:102` (`CARD_IMAGE_PATH_PATTERN` уже существует, но применяется
только в storageCleanup).

**Суть.** Шаблон валидного пути в коде есть, но на входе не применяется. Админ (или тот, кто
получил админ-токен) может записать произвольную строку до 500 символов: выйти за префикс
`cards/`, сослаться на посторонний объект бакета, вставить `../`. Побочный эффект: такой объект
навсегда невидим для уборщика — `selectOrphanCandidates` отбросит его как `skippedInvalidPath`
и никогда не удалит.

**План.**
1. В `cardImageInput.storagePath` заменить `requiredText` на `z.string().regex(CARD_IMAGE_PATH_PATTERN)`
   — вынести паттерн в `packages/contracts/src/constants.ts`, чтобы он был один на оба пакета.
2. В `publicImageUrl` пропускать сегменты через `encodeURIComponent`.
3. Тест: путь вне `cards/` и путь с `../` отклоняются с 400.

### 10. `validateWidgetLogin` строит data-check-string из zod-очищенного объекта — 5/10

**Где:** `backend/src/lib/telegram.ts:166-171`, `packages/contracts/src/auth.ts:15-23`.

**Суть.** `widgetLoginInput` — обычный `z.object`, который по умолчанию **вырезает** неизвестные
ключи. Строка для проверки подписи собирается из уже очищенного объекта. Как только Telegram
добавит в Login Widget новое поле, оно выпадет из data-check-string, подпись перестанет
сходиться и вход в браузере сломается — целиком, молча и без изменений с нашей стороны.
Классическая мина замедленного действия во внешней интеграции.

**План.**
1. Принимать сырой объект (`z.looseObject` / `.passthrough()`), строить data-check-string
   из **всех** полученных полей кроме `hash`, и только после успешной проверки подписи
   валидировать структуру строгой схемой.
2. Тест: лишнее неизвестное поле в payload не ломает верификацию.

### 11. Cross-card удаление фото при совпадающем `storage_path` — 4/10

**Где:** `database/migrations/0001_initial_schema.sql` (`card_images_card_path_unique (card_id, storage_path)`),
`backend/src/repos/adminCatalog.ts:updateCard` / `deleteCard`,
`backend/src/routes/admin/cards.ts:64,76` (`deleteStorageObjects(removedPaths)`).

**Суть.** Уникальность пути — только в пределах карточки. Один и тот же `storage_path`
может быть привязан к двум карточкам (через восстановленный черновик в localStorage или
параллельное редактирование в двух вкладках). Тогда удаление фото у карточки A физически
удалит файл, на который ещё ссылается карточка B — у неё останется битая ссылка.

**План.**
1. Перед `deleteStorageObjects` фильтровать пути через `findReferencedStoragePaths`
   (функция уже есть в `repos/cardImages.ts`) — удалять только то, на что не ссылается
   ни одна другая карточка.
2. Опционально: глобальный `unique (storage_path)` на `card_images` — сделает ситуацию
   невозможной по построению.

### 12. `save_chat` молча перезаписывает настроенный `adminChatId` — 4/10

**Где:** `backend/src/routes/telegram.ts:30-38`.

**Суть.** `clear_chat` и `migrate_chat` аккуратно сверяются с текущим значением,

### 13. Ручной `bun run build` откатывает CSP в Report-Only — 4/10

**Где:** `webapp/scripts/generate-headers.ts:34-35`, `DEPLOYMENT.md`.

**Проверено на проде:** заголовок отдаётся как **enforcing** `Content-Security-Policy` — сейчас

**Суть.** Enforcing включается только переменной `CSP_ENFORCE=1`, которая задана в

и незаметно снимет CSP с прода.

**План.**
1. Инвертировать умолчание: enforcing по умолчанию, а `CSP_REPORT_ONLY=1` — явный opt-in для отладки.
2. Добавить в чек-лист деплоя проверку живого заголовка:
   `curl -sI https://agromarketkz-webapp.pages.dev/ | grep -i '^content-security-policy:'`.

## Что проверено и оказалось в порядке

Чтобы объём работ был реалистичным — вот что аудит подтвердил как корректное:

- **Проверка подписи Telegram.** HMAC-цепочки для `initData` (`HMAC("WebAppData", token)`)
  и Login Widget (`SHA256(token)`) реализованы по спецификации, сравнение хешей
  константное по времени, `auth_date` проверяется.
- **JWT.** `hono/jwt` сверяет `header.alg` с ожидаемым — подмена на `none`/RS256 невозможна.
  Claims валидируются zod, есть версия сессии для отзыва.
- **SQL-инъекции.** Весь доступ к БД — через tagged templates `postgres.js`; динамические
  списки колонок собираются через `sql(columns, ...keys)` с ключами из белого списка.
  Инъекций не найдено ни в одном репозитории.
- **IDOR.** Все пользовательские выборки скоупятся по `user_id` из токена; админские
  маршруты закрыты `requireAuth + requireAdmin` на уровне группы, а не отдельных обработчиков.
- **XSS.** Ни одного `dangerouslySetInnerHTML`, `innerHTML`, `eval` во всём фронтенде.
  Внешние ссылки проходят через allowlist схем (`openExternalLink`), t.me-ссылки —
  через отдельную проверку. HTML для Telegram экранируется (`escapeHtml`).
- **CSP на проде — enforcing** (проверено live), с точными origin вместо wildcard,
  `frame-ancestors` ограничен доменами Telegram, `object-src 'none'`, `base-uri 'self'`.
  Плюс HSTS с preload, `Permissions-Policy`, `nosniff`.
- **CORS.** Проверено live: preflight с посторонним Origin не получает
  `Access-Control-Allow-Origin` — браузер запрос заблокирует.
- **Ограничение размера тела** 256 KiB работает и для `Content-Length`, и для чанкованного
  потока — есть тесты на оба пути.
- **Идемпотентность заявок** через `clientRequestId` + хеш полезной нагрузки продумана
  тщательно: повторная проверка после взятия блокировки строки пользователя, обработка
  гонки на `on conflict do nothing`, различение «тот же запрос» и «переиспользованный id».
- **Реконнект к БД** на Workers: ретраятся только одиночные запросы, транзакции — нет,
  с корректным обоснованием неоднозначности COMMIT.
- **Ответы об ошибках** не протекают: `ZodError` схлопывается в общее сообщение
  без `issues` и путей, есть тест именно на это.
- **Секреты** не в git: `.env`, `.dev.vars`, `dist/` не отслеживаются, история чистая.
- **Уборка Storage** написана аккуратно: grace period, повторная сверка ссылок
  непосредственно перед удалением, строгий учёт частичных сбоев, лимиты на запуск.
