## 2. Итоги обсуждений

### 🔴 Критическая находка — миграция 0006 не применена к продовой БД

Независимо подтверждено тремя способами: (а) агент best-practices проверил напрямую через Supabase MCP, (б) я лично перепроверил тем же способом (`list_migrations`, `information_schema.columns`) — колонки `token_version` в `public.users` нет, `0006_user_token_version.sql` отсутствует среди применённых миграций (применены только 0001/0002/0003/0007/0008); (в) регрессионный агент построчно проследил механику поломки в коде.

**Механизм отказа при деплое as-is:**
- Новый логин: `row.token_version` из `returning *` равен `undefined` → `JSON.stringify` в `sign()` теряет ключ `ver` → `tokenClaimsSchema.superRefine` требует «оба claim'а (`ver`/`iat`) или ни одного» → свежевыпущенный токен сразу проваливает валидацию → `401`.
- Любой другой запрос (включая legacy-токены): `findAuthUser` (`repos/users.ts:46-51`) явно селектит `token_version` → Postgres кидает `column does not exist` → это исключение **не обёрнуто** в try/catch (он есть только вокруг `verifyToken` в `middleware/auth.ts`) → улетает в `app.onError` как generic `Error` → **500**.

**Итог: полный отказ всей аутентифицированной части API** (`/profile`, `/catalog`, `/requests`, `/feedback`, `/admin/*`, `/favorites`, зарегистрированная часть `/settings`) сразу после гипотетического деплоя. План сам предвидел этот precedence-риск (§13 — миграции перед деплоем backend, §16 — явная зависимость), но по факту порядок нарушен на реальном проекте.

### 🟠 CSP / Login Widget — реальная, не гипотетическая несовместимость

Агент best-practices настоял на этом после моего давления понизить до «подождём Report-Only QA»: `script-src` не содержит `unsafe-eval`, а виджет Telegram (`data-onauth="onTelegramAuth(user)"` в `LoginScreen.tsx`) вызывает `eval()` через `window.__parseFunction` (подтверждено чтением реального `telegram-widget.js`). Это детерминированный факт архитектуры CSP-политики, проверяемый уже сегодня без деплоя — не эмпирическая неизвестность, которую «поймает» Report-Only. Ключевой аргумент, который убедил меня: отказ **тихий** — виджет рендерится, OAuth-попап закрывается штатно, но колбэк логина просто никогда не вызывается, без видимой ошибки пользователю; заметить можно только специально открыв DevTools и проверив CSP violation report на `eval` именно в момент клика по виджету.

**Согласованный вывод:** нужен код-фикс, а не запись «дождёмся QA»: либо узкий `unsafe-eval` carve-out (в идеале scoped/hash), либо переключить `LoginScreen.tsx` с `data-onauth` на `data-auth-url` (redirect-колбэк Telegram, не требующий eval — чище).

### 🟡 `webapp/src/lib/api.ts::handleUnauthorized` — синхронный throw обходит защиту

Сигнатура `setUnauthorizedHandler` обещает поддержку `() => Promise<void> | void`, но `unauthorizedHandler()` вызывается ДО `Promise.resolve(...)` — синхронный throw вылетает мимо recovery-гейта, а не попадает в цепочку `.finally`. Сейчас не триггерится (единственный вызывающий код в `auth.tsx` — `async`-функция), но баг-агент убедительно показал: это нарушение собственного публичного контракта типа, а не «придуманный сценарий», и цена бага при срабатывании — не косметическая (ломается ровно та гарантия «параллельные 401 не запускают несколько re-login», ради которой модуль существует, плюс наружу утечёт не-`ApiError`, ломая downstream `instanceof`-проверки).

**Согласованная рекомендация — починить сейчас, дёшево и без риска:**
```ts
unauthorizedRecovery = Promise.resolve()
  .then(() => unauthorizedHandler())
  .finally(() => { unauthorizedRecovery = undefined; });
```

### 🟡 Load-test раннер не проверяет заявленный сценарий

Регрессионный агент изначально назвал риск контенции пула (`max: 3`) с новым `FOR UPDATE`-локом в `feedback.ts` "регрессией". После спора: ярлык снят (это осознанный trade-off по самому плану, L4, не побочный эффект) — но при этом агент нашёл конкретный, более узкий и реальный пробел: `executeMutationFlow` в `e2e/scripts/loadTest.ts` вызывает `/requests`/`/feedback` **последовательно** для одного пользователя (параллелизм раннера — только между разными пользователями). Значит заявленный acceptance-gate (план, раздел M5 п.5: «одновременные requests/feedback») **не тестирует** именно intra-user конкуренцию за лок на строке `users`, которая и есть источник риска. Gate закроется «зелёным», не проверив то, ради чего он введён.

### 🟢 Всё остальное — подтверждено как правильно сделанное

- Атомарный анти-спам лимит (L4): TOCTOU закрыт корректно, лок + проверка внутри одной транзакции до insert — подтверждено чтением кода двумя агентами.
- CORS: точный origin, без credentials — не рубеж против CSRF, но и не должен им быть (авторизация чисто через Bearer).
- Storage RLS: `deny-all` подтверждён напрямую запросом к `pg_policy` на живом проекте — anon/authenticated не могут писать/удалять ни при каких условиях.
- `search_path` фикс — единственная функция в схеме, других уязвимых не пропущено (проверено на живой БД).
- `requireRegistered` — семантика 1:1 со старым кодом, второй SELECT реально убран.
- `telegramLink() → string | null` — все 4 места вызова в webapp обрабатывают `null` корректно, нет утечки `https://t.me/null`.
- DI (`createRequireAuth(authUserLookup = findAuthUser)`) — оправдан: единственный способ протестировать HTTP-поведение rate-limit middleware без живой БД; в проекте нет `mock.module`/`spyOn`, соседние middleware DI не имеют, потому что оно им не нужно.
- Структуры `storageCleanup.ts` (`OrphanSelection`, `CleanupSummary`) — нужны для тестируемости чистой функции отбора кандидатов и для observability прод-cron-джобы, не gold-plating.
- Cloudflare rate-limit `namespace_id` — риск коллизии явно закомментирован как pre-deploy checklist item, не скрытая регрессия.

### 📉 Про «меньше кода» — главный вопрос заказчика

- **Единственная содержательная находка:** упрощение regex в `packages/contracts/src/telegramContact.ts` — 16 строк → 4, поведенчески проверено на 27 тестовых кейсах, эквивалентно оригиналу. Опционально, чистая косметика.
- **Дедупликация rate-limit SQL** (`requests.ts`/`feedback.ts`) — **не стоит**. По моей просьбе агент пересчитал узкий вариант helper'а (без слияния разнородных lock-запросов) и honestly показал, что моя изначальная оценка экономии (~7 строк) была ошибочной — не учла обязательный импорт типа `TransactionSql` и doc-комментарий по конвенции файла. Реальный итог — **минус 4-5 строк**, кодовая база растёт, а не сокращается.
- **4-кратное дублирование replay-check в `repos/requests.ts`** — реальное, но **вне скоупа**: подтверждено `git show 949a176:...` — паттерн существовал байт-в-байт до начала работы по security-плану, security-коммиты его не трогали структурно, только вставили новый код между существующими блоками.
- Прочие кандидаты на сокращение (DI в auth, `superRefine` вместо `z.union`, структуры storageCleanup, Promise-гейт в api.ts, split vs `new URL` в rate-limit middleware) — рассмотрены и отклонены с конкретным обоснованием: либо экономия отрицательная при честном подсчёте, либо сокращение стоит потери тестируемости/корректности.

## 3. Моё мнение

Работа по плану реализована добросовестно и в большинстве пунктов подтверждена тестами — это не security-theater, а рабочая атомарная защита (TOCTOU в rate-limit, RLS deny-all на Storage, точный CORS, безопасная канонизация telegram-контактов). Попытки найти «избыточный код» в основном подтвердили, что текущие решения уже близки к минимальным при сохранении заявленных гарантий — сокращать почти нечего без потери корректности.

Но релиз **не готов**: один настоящий deployment-блокер (миграция 0006 не применена к прод-БД) и одна конкретная, недорогая в починке несовместимость (CSP/Login Widget), которые план архитектурно предвидел, но которые фактически не были доведены до конца на момент этого ревью.
